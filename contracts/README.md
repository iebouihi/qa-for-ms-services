# Contracts

Two kinds of contract, two purposes:

| | Specification (`openapi/`, `asyncapi/`) | Consumer-driven contracts (`pacts/`) |
|---|---|---|
| Says | Everything a provider offers | Exactly what each consumer uses |
| Written by | Provider team | Consumer team, generated by its tests |
| Used for | Documentation, mocks, virtualization | Blocking a breaking change before deployment |
| Checked by | Review, linting | Provider build (`*ContractTest`), on every PR |

## Pact flow in this repository

```
cart-service (consumer)                      product-service / customer-service (providers)
ProductClientContractTest       ──writes──►  contracts/pacts/cart-service-product-service.json   ──verified by──► ProductApiContractTest
CustomerRegisteredContractTest  ──writes──►  contracts/pacts/cart-service-customer-service.json  ──verified by──► CustomerEventsContractTest
```

The Maven reactor builds cart-service first, so pacts exist before providers verify them.
`contracts/pacts/` is generated (git-ignored) and published as a CI artifact.

**At scale**, the folder is replaced by a Pact Broker (or PactFlow): consumers publish
pacts tagged with their version, providers verify all deployed consumer versions, and the
pipeline asks `pact-broker can-i-deploy --pacticipant cart-service --version $SHA --to-environment staging`
before every deployment. That gate is what lets each service release independently.
